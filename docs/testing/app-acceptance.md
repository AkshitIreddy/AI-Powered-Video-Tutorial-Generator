# App acceptance harness

The app acceptance harness checks the complete deterministic-safe desktop
lifecycle without provider credentials, model weights, GPU work, or network
access. Run it from the repository root:

```text
node scripts/run-app-acceptance.mjs
```

The command fails on the first broken layer. It performs:

1. A production desktop web build, including TypeScript validation.
2. A Playwright app journey that creates and saves an explicit all-local
   provider profile, creates a project, imports a private Markdown source,
   reviews the provider boundary and budget, approves the learning plan,
   enters Review, configures Export, archives the project, and submits a master
   export. Page errors and browser console errors fail the test.
3. An authenticated sidecar journey that initializes the real project folder
   and SQLite database, starts durable generation, polls to the approval wait,
   approves it, polls every generation stage to success, submits a durable
   master-export job, verifies its promoted master and sidecars, and creates a
   non-empty `.alytutorial` archive.

Focused diagnostic runs are available:

```text
node scripts/run-app-acceptance.mjs --protocol-only
node scripts/run-app-acceptance.mjs --ui-only
node scripts/run-app-acceptance.mjs --ui-only --skip-build
```

`--skip-build` is only for diagnosing a known compile failure. It is not valid
release or acceptance evidence.

## Evidence and interpretation

Playwright writes screenshots and failure traces under
`apps/desktop/test-results/`. The successful app journey captures the full
Export workspace and the export-settings panel. The Python test uses a
temporary project directory and verifies the durable files before the test
fixture removes that directory.

Passing this harness means the deterministic app contract and authenticated
sidecar contract agree across the project lifecycle. It does **not** mean a
production tutorial was generated by live AI or encoded by the production
media toolchain.

| Layer | Automated here | Explicit boundary |
|---|---|---|
| React user journey | Yes, through Playwright | Runs the browser-demo command adapter |
| Provider policy and budget UI | Yes | Uses an all-local no-secret test profile |
| Tauri/Rust command broker | No | Covered by Rust tests, not this Playwright process |
| Authenticated Python sidecar | Yes | Direct loopback protocol, same allowed desktop methods |
| Durable generation and approval | Yes | Local deterministic adapters |
| Master export and sidecars | Yes | Explicit fixture renderer, not Chromium/FFmpeg media |
| Portable project archive | Yes | Real archive written and size-checked |
| Live cloud provider calls | No | No key or network use |
| Local model inference | No | No weights or GPU use |
| Presenter/lip-sync composition | No | Requires the real media acceptance run |

## Native GUI automation blocker

Playwright controls Chromium through its browser protocol. The packaged Tauri
2 application hosts the UI in Windows WebView2, and this repository does not
expose a test-only WebView2 debugging endpoint or desktop automation driver.
On the Windows test machine checked on 2026-08-29, WinAppDriver, Appium, and the
PowerShell UIAutomation module were not installed. Consequently, attaching
Playwright to the packaged native window is not currently a repeatable or CI
safe path.

Computer-use automation can inspect the native window interactively, but it is
not a deterministic acceptance harness and cannot replace file, database,
provider-usage, or media assertions. A native production acceptance result
must therefore pair interactive desktop control with durable project evidence,
provider usage records, model/runtime manifests, GPU/process telemetry when
applicable, `ffprobe`/audio QA, and inspection of the exported full tutorial.

The user-facing “full tutorial” gate remains separate and stricter: the app
must create, approve, generate, monitor, review, and export a complete tutorial
using the selected real providers and local models; the presenter artifact must
be visibly composited into the final video; and the resulting full-duration
media must pass technical QA and human visual inspection.
